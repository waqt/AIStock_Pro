## 1.4 设计原则

### 核心原则

| # | 原则 | 说明 | 反面案例 |
|---|------|------|---------|
| P1 | **渐进增强** | 不改架构骨架, Agent 内部升级 | ❌ 重写 DAGOrchestrator 核心 |
| P2 | **LLM 定性, 程序化定量** | Step 2 归类, Step 3-8 算分 | ❌ 让 LLM 给 scarcity_score=9.2 |
| P3 | **案例驱动** | GPT V2 产业案例嵌入 few-shot | ❌ 空泛的通用 prompt |
| P4 | **可独立测试** | 每个 Agent 可单独 curl 验证 | ❌ Agent 间硬耦合 |
| P5 | **确定性优先** | 关键结论程序化生成 | ❌ 纯 LLM 输出的数字 |
| P6 | **可追溯** | 每个判断回溯到数据源 | ❌ "AI 分析认为..." |
| P7 | **向后兼容** | 现有 API/前端/DB 不受影响 | ❌ 改变 API 返回格式 |

### LLM 使用边界

```
LLM 该做的 (逻辑归类, 强项):
  ✅ 这个行业处于 bottleneck_formation 阶段 — 模式识别
  ✅ 景气类型是 supply_shock — 归类判断
  ✅ 需求是真实终端消费, 不是补库 — 逻辑推理
  ✅ 资源迁移方向: HBM 挤占 DDR — 产业链推演
  ✅ 隐性受益者: 成熟制程测试厂 — 第二层思维

LLM 不该做的 (数字化评分, 弱项):
  ❌ scarcity_score = 9.2 — 无法验证
  ❌ alpha_score = 92 — 不知道怎么来的
  ❌ 目标价 = 156.8 元 — 精确数字不可靠
  ❌ 概率 = 73% — 缺乏统计基础
```

## 1.5 术语表

| 术语 | 说明 |
|------|------|
| **Pipeline** | 一次完整的 Step1-11 分析流程 |
| **Run** | Pipeline 的一次执行实例, 由 run_id 标识 |
| **Step** | Pipeline 中的一个分析步骤 (如 Step 2 看门人) |
| **Agent** | 执行特定 Step 的智能体实例 |
| **Checkpoint** | 某个 Step 完成后的输出快照 (JSON 文件) |
| **Trace Log** | 某个 Step 的完整推理过程日志 (搜索+LLM+证据链) |
| **Manifest** | 一次 Run 的元信息 (所有 Step 状态 + 时间 + 错误) |
| **DAG** | 有向无环图, Agent 之间的依赖关系 |
| **Thesis** | 投资论点 (如 "HBM 紧缺至 2027") |
| **Falsification Signal** | 论点证伪信号 (如 "HBM 价连续 3 月下跌") |

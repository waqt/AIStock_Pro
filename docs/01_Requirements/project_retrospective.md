## 二、做得好的

### 1. 系统性开发流程
`需求文档 → 设计 Plan → 代码实现 → 验证 → 提交` 五步闭环。每次实现前先做现状审计（什么已有、什么缺失、什么假数据）。

### 2. DDD 分层纪律
`api/` 只做路由校验，`core/` 做基础设施，`quant/` 做领域逻辑。Gemini 时代的数据层反向依赖（TaskManager→AnalysisTask）已清理干净。

### 3. 老项目资产复用
不是盲目照搬代码，而是提取已验证的模式（Prompt、AI 链式调用、数据源工厂），适配新架构后重新实现。API Key 直接从老项目迁入。

### 4. 多源数据架构
DataRouter → AkShare/Sina 优先级+自动降级，比老项目的单一数据源更可靠。港股通过 akshare 库解决了新浪接口不支持的问题。

### 5. 前端体验一致性
暗色主题贯穿所有页面（Modal 弹窗、跑马灯、任务监控、详情弹窗），不再有白色 alert 框。

### 6. Git 版本管理
18 次提交粒度合理，commit message 清晰标注 feat/fix/chore，每次提交可独立回滚。

## 三、存在的问题

### 1. Bug 修复占比过高

18 次提交中 7 次是"修 Bug"（38%）。这些 Bug 如果在开发阶段就验证，大部分可以避免：

| Bug | 根因 | 如何提前发现 |
|-----|------|-------------|
| AnalysisTask 残留 | Gemini 未清理干净 | 全局 grep + 启动验证 |
| run_task params 传参错误 | 未读 TaskEngine 源码 | 单测/冒烟测试 |
| ORM identity map 不刷新 | SQLAlchemy 异步特性 | DB 数据验证 |
| 数字守护吞噬负成本 | 边界条件 `<=0` | 负成本测试用例 |
| profit_loss_ratio 为 null 导致 500 | Schema 类型不匹配 | API 冒烟测试 |

### 2. 缺乏冒烟测试脚本

每次改完后依赖"启动服务→手动点击→看日志"来验证。如果有一个 `scripts/smoke_test.py` 脚本，每次提交前跑一遍（调用 5-8 个关键 API 检查返回值），大部分回归问题都能当场发现。

### 3. 环境依赖的脆弱性

- AkShare 内用 `requests` 库受系统代理影响，时好时坏
- 新浪 A 股接口可用但港股不行
- 腾讯财经 K 线接口参数格式难以确定
- open.er-api.com 被墙

最终解决方案（新浪 hq.sinajs.cn）是经过 3 轮试错才找到的。

### 4. 数据类型边界处理不完整

`profit_loss_ratio` 允许 null 这个决策，应该在一开始设计负成本 P&L 时就同步更新 Schema 和前端显示。实际开发中分了两次提交。

### 5. 文档与代码不同步

导入模块的规格文档是用户提醒后才补的。理想状态是：模块开发完成 → 同时产出规格文档。

## 四、改进措施

### 立即执行

1. **创建冒烟测试脚本** `scripts/smoke_test.py`
   - 启动后调用 8 个关键 API 检查返回码
   - GitHub Actions / 手动在提交前跑

2. **代码提交前自检清单**（更新 engineering_standards.md）
   - [ ] 新增/修改 API → 冒烟测试通过
   - [ ] DB Schema 变更 → 迁移脚本 + 验证
   - [ ] 字段允许 null → Schema 和前端同步处理
   - [ ] 全局 grep 残留引用

### 后续改进

3. **环境容错**：数据源增加健康探测 + 缓存降级，避免 HTTP 404/超时导致白屏
4. **Schema 变更影响分析**：修改 models.py 时，同步检查 schemas.py 和前端
5. **文档即交付物**：新模块开发完成后，规格文档与代码一同提交
